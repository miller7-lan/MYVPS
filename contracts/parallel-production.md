## SQLite lock repair and recurrence prevention
The first parallel deployment exposed an existing-DB raw-descriptor bug: Store initialization performed os.open/os.close on an already SQLite-managed database. On Linux, closing another descriptor for the same inode in the same process can release traditional POSIX file locks. The observed incident involved deleted-but-open WAL/SHM and inconsistent views between agent and control connections. Repeated RPC, deleting WAL/SHM or rebuilding the database is not a repair.

Existing databases are now opened by SQLite without any extra raw open/close. Only a genuinely missing database may be created with O_CREAT|O_EXCL|O_NOFOLLOW, with concurrent-creation, symlink and permission checks. Release7b59b5cc8f22804c98211690 contains the lock repair; all six dedicated regression checks passed on target Linux. Future server releases must retain the external-process lock regression. Hashing/copying the active DB from another raw descriptor inside the SQLite-owning process is prohibited; normal backups use SQLite-consistent backup mechanisms.

Program-only repair first quiesces new control requests, preserves the main DB and all WAL/SHM branches (including deleted-open files), and stops ONLY new agent/subscription/helper socket with no active helper instance. The existing legacy services are never stop targets. deployment/repair.py binds the original genuine install authorization and exact preview SHA. Its narrow change scope is store.py plus the repair/packaging module; it stages a new immutable release/venv, self-tests only temporary DBs, and atomically changes current. It does not open production SQLite, restore old state, modify root policy/registry/TLS/units/firewall/accounts/core, or start services. Operator-controlled restart and fresh production verification follow separately. Prior release, ledger, permanent revocations and authorization/repair receipts remain preserved; a known-bad lock implementation must not be restored merely because its files remain available.
