# 保持现有名单用户可用的升级验收

当前约束是：增加注册与审核功能时，保留现有名单用户的代理。此前允许普通成员短暂停用的清单已作废，不能继续使用。以下内容是**本地候选方案**：已有单元测试和一次性 systemd 隔离演练，**尚未部署，也不能称为已支持生产“无中断升级”**。

## 保留范围

- 保留每位现有用户的凭据、订阅、端口、额度和已用流量。
- 不重启现有代理进程，不主动关闭已有连接，不把用户移出名单再加回。
- 不重建管理员已经清理的旧代理。
- 不修改 SSH、管理密钥或其他服务。
- 注册、邮件与网页上线不得自动更换现有用户的凭据。

## 为什么分两个阶段

当前普通用户的代理 `BindsTo` 原后台，直接重启后台会连带停止代理。另外，线上运行的 `44c4d8af…` 版本中，root helper 每次调用都会重新读取 `policy.json`，而且只接受 v1 策略。若先把策略换成 v2，旧后台的 helper 调用和 Mac 管理入口都会失败。因此拆成两步：

| 阶段 | 内容 | 不包含 |
|---|---|---|
| A：writer 交接（本候选） | 每成员独立 guard；新 writer 只读预热；成员依赖从旧 writer 转到各自 guard；同一把账本锁交接；切换 `current` | v2 策略、新端口、网页账号、防火墙、9443 替换、证书来源变更、开放注册 |
| B：注册资源（另行批准） | v2 资源池、web 账号与 Socket、5 个新槽、受管证书、门户 | — |

阶段 B 需要 writer 载入 v2 策略，届时用同样的 standby 交接方式换到另一个 release 实例，不重启当前 writer。

新版 helper 在 `/etc/dazzle-vps/guard-proofs` 存在时，v1 策略下也为成员写入 root 证明（v2 下仍为必需）。否则阶段 A 之后任何受控暂停或恢复都会让 guard 判定 PID 异常并停止成员。

## 一次性目标机协调器

`deployment/coordinator.py` 在目标机上以 root 一次运行，切换窗口内不依赖多次 SSH 往返：

- **预览（只读）**：重新观察所有输入并渲染每个将写入文件的全文。观察内容包括 unit 源及其 SHA、进程身份、`/proc/locks` 中的独占锁、账本事实（以 dazzle-agent 身份只读读取）和 TCP 见证。管理入口及其所在目录必须只有 root 可写，因为执行时要原地替换它，否则预览直接报错。预览还会实测三项：旧 writer 从启动到 READY 的时间、helper 延迟，以及 3 秒内旧 writer 自身节奏能提供的最小成员样本年龄，据此估算回退所需时间。
- **批准**：单独的批准文件绑定计划 SHA，并逐项确认三点：宁可中止也不重启 Core；回退属于尽力而为、guard 保持 fail-closed；注册保持关闭。
- **执行**：由新 release 自身运行，进度写入 `/etc/dazzle-vps/handoff/<plan_id>/receipt.json`，意外异常的类型和消息记入其中的 `unexpected_error`。中断信号只在停止旧 writer 之前生效。建议用 `systemd-run` 运行，避免 SSH 断开。

执行顺序：

1. 重新推导计划，任何已审事实（PID、InvocationID、重启数、文件 SHA、锁 inode、revision）变化即中止。
2. **暂停管理入口**：固定 launcher 被临时替换为返回 `CONTROL_UNAVAILABLE` 的保持脚本；等待在途 RPC 全部结束，退出时恢复原字节。这是对并发管理的实质阻断，而不只是口头要求暂停 App。
3. 每个成员必须有**真实 VLESS TCP 见证**：Core 自身持有的 socket 中，本地端口为该成员公开端口的 ESTABLISHED 连接。统计 API 会话（回环 API 端口）和出站连接不计入。闸门只认从准备开始前一直保持到闸门时的同一连接，短暂出现的扫描或 REALITY 回落连接不能顶替；没有见证就不切换。见证只记录 inode 数量，不记录对端地址。它仍不能从密码学上证明连接已通过 VLESS 认证，所以真实客户端需另行确认。
4. 私密一致性备份，转为 rollback journal、不留 sidecar 文件；在备份副本上运行新版本的附加式迁移检查。永不自动恢复数据库。
5. 写入准备文件，然后 daemon-reload，旧 writer 进程保持不变。准备文件包括：v1 策略字节快照、固定新 release 路径的 guard 模板、以 release ID 为实例名的 writer 模板、固定旧 release 与 v1 快照的旧 writer 回退定义。
6. 启动每个成员的 guard，必须 READY 且 `phase=running`。
7. 启动新 writer standby，必须为 `standby-ready; writer=false`，锁 inode 相同，状态在 1 秒内刷新过。
8. 先在运行时放开每个成员的网络闸门，再写入完整成员实例 unit 和闸门 drop-in。实例 unit 只改 `[Unit]`：去掉 `BindsTo`，把 guard 加进 `Wants`，并用它替换 `After` 里的旧 writer，整个 Service 段保持不变。drop-in 默认关闸。daemon-reload 后读回：成员不再绑定任何单元，guard 在 Wants/After 中，闸门处于放行状态，FragmentPath 为实例文件，drop-in 只有闸门这一个，Core 的 PID、InvocationID 与 NRestarts 均未变。
9. **闸门**，任一项不满足即撤回准备并中止：
   - 管理入口已暂停且静止；policy 与 registry 未变；
   - 旧 writer 是同一进程并独占锁；standby 状态新鲜；guard 与 Core 都是同一进程；每个成员的闸门处于放行状态；
   - 账本的 revision、任务、事故数和周期均未变；成员可信、已授权、未接近额度，管理员周期边界不临近；
   - 样本 ≤2 秒；见证存在。
10. 旧 writer 每个 worker 各有自己的 1 秒帧相位，帧还要等 0.5 秒一次的写入循环才落库，所以落库样本年龄不会同时归零。协调器先观察至少一个周期，选在成员样本年龄接近该周期最小值的时刻才停。条件是 `5 − 成员年龄 − 接棒期限1.2 − 余量0.25 ≥ 实测回退时间`，且管理员样本加同一窗口不超过 5 秒。成员的 guard 截止时间从读取样本的那一刻起算。**余量不足就不停止旧 writer**，按预览实测相位计算不足时，计划也不会进入可批准状态。真正停止前还要再读一次 CPU steal：自核对计划以来，宿主机暂停本虚拟机的累计时间超过 0.2 秒就中止（见下文“宿主机停顿”）。
11. 接棒：新 writer 必须 READY、独占锁，所有 worker 都有停止之后的新持久化样本。旧 writer 0.8 秒未退出则 SIGKILL。新 writer 一旦已就绪并独占锁，无论状态文字如何都不再回退，因为冷启动回退只会更慢；样本无法确认时标记为待人工复核。
12. 失败回退：停止新 writer（含 auto-restart 状态），启动固定版本的旧 writer。只有旧 writer 重新取得真实新鲜样本之后，才恢复成员对它的依赖：删除闸门 drop-in，再在运行时放开闸门，然后停止 guard。超过时效时，guard 关闭成员的网络闸门（公网流量暂停，Core 保留），恢复依赖时重新放开；收据分别写明 Core 被中断的人数和流量曾被暂停的人数。
13. 验收观察 3 秒，同时满足：
    - 只有一个持锁 writer，样本持续推进，没有新事故；
    - 每个 worker 的已用量增量与原始累计差完全相等；
    - guard 与 Core 均未重启，成员闸门始终放行，见证连接至少一条仍存活。
14. 完成：`current` 切到新 release；安装未来成员模板：用 Wants 关联自己的 guard，并默认关闸（此时现有成员都已有完整实例 unit）；旧 writer 取消开机启动但不重建 alias，新 writer 启用；恢复管理入口。然后用新代码实际运行一次已安装的证书同步并核对结果。同步失败不撤回交接，收据状态为 `handoff_complete_certificate_sync_failed`；校验失败时不会替换现有证书，但须在其到期前修复。

## 证书同步与 `current` 的关系

证书来自 certbot 维护的 `qqg-ip`，这是 Let's Encrypt 的短期 IP 证书，有效期不到 7 天。服务器上的同步已不再读取旧 `/etc/s-box`，而是由三个在发布包之外安装的文件完成：drop-in `20-direct-acme.conf`、脚本 `/usr/local/libexec/dazzle-certsync-from-acme.py` 和 certbot 部署钩子。三者的原文已逐字节记入仓库 [`server/certsync/`](../server/certsync/)。

脚本使用 `current` 指向的 release 的解释器，并从中导入 `deployment.certsync`，所以阶段 A 切换 `current` 后会改用新代码。契约测试 `deployment/tests/test_server_certsync.py` 用新 release 实际执行该脚本。2026-10-26 又对线上证书做了只读核对：新版本更严格的到期、IP、配对和文件属主检查全部通过。

## 宿主机停顿（2026-10-25 线上事件）

2026-10-25 19:51 和 19:52（北京时间），线上旧 writer 两次被 systemd 看门狗（10 秒）结束。只读排查的结论是宿主机暂停了这台 KVM 虚拟机，而不是程序卡死：

- 内核依次报告 clocksource 读数间隔 1.2 秒、7.9 秒和 29.5 秒，并出现 `RT throttling activated`。
- 同一时段系统日志完全空白，开机以来累计 CPU steal 约 30 秒，几乎全部落在这一分钟内。
- 两次看门狗超时都发生在暂停恢复的同一秒。helper 调用显示的 32 秒 CPU，应是暂停期间的时间被记到了正在运行的进程上；helper 代码里只有带期限的短暂等待，没有空转循环。helper 的错误输出被设为 `StandardError=null`，因此无法确认那两次调用的具体操作。

后果：成员代理在 BindsTo 作用下随旧 writer 停止约 53 秒，由重启后的 writer 自动拉起。但它的计量被记为不可用（未知用量），直到 21:15 从管理 Mac 执行 `meter.reconcile`，那次对账又重启了一次成员的 Core。

对阶段 A 的影响：如果成员仍绑定 guard，同样的暂停会让 guard 被看门狗结束，成员随之被停止，此后需要人工对账才能恢复，影响比 44c4 更大。现在成员不再绑定 guard，而是由网络闸门保护（见下文）：暂停结束时，guard 被结束后闸门关闭，Core 保留；guard 自动重启，样本恢复后再放开。为减少在不稳定时段交接，另加了两道检查：

- 预览读取最近 24 小时的内核停顿记录（`journalctl --dmesg`），有记录就不可批准（`HOST_STALLS`）。观察相位期间出现 steal 同样不可批准（`HOST_STEAL`）。
- 执行时，停止旧 writer 之前若 steal 增长超过 0.2 秒，就中止并撤回，旧 writer 不停。
- 两个阈值都是已审参数，可用 `--preview --parameters <JSON>` 在允许范围内调整，并由计划和批准一并绑定。

这些检查只能避开已知不稳定的时段，无法阻止交接之后再发生的暂停。5 秒保护仍按挂钟计算，没有改变。

## 成员网络闸门

每个成员的 Core 现在由一道网络闸门保护，而不是在计量中断时被停止。闸门就是成员自己 unit 上的 `IPAddressDeny=any` 和 `IPAddressAllow=localhost`：关闸时只拦公网流量，回环不受影响，所以 writer 仍能通过统计接口取样，Core 的进程和计数都保留。闸门由 guard 的 unit 以 root 身份操作（`deployment/member_gate.py`）：

- guard 确认样本新鲜后发出 READY，`ExecStartPost` 随即放开闸门。
- guard 进程的任何一次退出都会触发 `ExecStopPost` 关闸，包括样本过期、被看门狗结束、崩溃和主动停止。
- 成员身份或授权异常时，guard 以 3 退出：此时停止 Core，guard 不再重启。
- 闸门无法确认关上时，同样停止 Core。所以任何情况下都不会比原来的 BindsTo 更不安全。

时限：guard 在样本超过 4 秒时关闸，赶在不变的 5 秒保护之前生效；看门狗仍是 5 秒。guard 以 75 退出时自动重启，在样本恢复新鲜之前一直等待，等待期间闸门保持关闭。

只有已接管的成员（带闸门 drop-in）和使用新模板的成员才受闸门管理，因此接管之前、或回退之后，guard 的启停不会影响任何成员。

2026-10-26 在一次性容器（systemd 255）中实测了以下行为：

- **为什么不能用 `systemctl freeze`：**冻结会让统计接口也停止响应，没有新样本就无法放开。
- **为什么不能保留绑定：**guard 被看门狗结束时，`BindsTo` 会连带停止成员（`RestartMode=direct` 也一样），`Requires` 则会连带重启成员。所以成员改为 `Wants`。
- **闸门本身：**运行中加上或解除闸门都在毫秒级生效，已有连接在闸门恢复后继续传输。
- **slice 要求：**成员必须直接位于 `system.slice`；在嵌套 slice 里，systemd 255 关闸后无法再放开。预览会检查这一点（`MEMBER_SLICE`）。

尚未覆盖的部分：writer 仍按"样本间隔超过 5 秒即需对账"的规则处理。所以较长的 writer 中断或虚拟机暂停结束后，闸门会保持关闭，Core 不受影响，直到对账完成。要做到自动恢复，需要 writer 在有 root 闸门证明时接受这段计数连续的间隔。这部分代码属于 `backend/dazzle/domain.py`，与另一个会话正在进行的修改重叠，需先协调。

## guard 持有持久只读连接

演练中发现：WAL 数据库的最后一个连接关闭时，SQLite 会删除 `-wal/-shm`；guard 的状态路径只读，无法重建它们。原 guard 每次检查都重新打开连接，旧 writer 一关闭，它下一次打开就会失败，成员会被立即停止。交接时也存在这一风险，演练里只是恰好有协调器的读连接撑着。

现在 guard 改为始终持有一条只读连接，每轮使用独立的读事务，等待期间不占用快照。fail-closed 完全由未改变的 5 秒账本时效决定。加入网络闸门之前的隔离演练中，writer 停止后约 4.9–5.2 秒成员被停止，管理员不受影响；现在改为约 3.5 秒关闸、Core 保留。

## 必须满足的检查

| 检查 | 合格标准 |
|---|---|
| 原用户身份 | 用户 ID、凭据版本、配置摘要和端口不变 |
| 代理进程 | PID、InvocationID、进程启动时间及重启次数不变 |
| 正在使用的连接 | 每个成员至少一条预先存在的 VLESS TCP 会话在交接后仍存活；TUIC 与真实客户端另行验收 |
| 计量 | 累计上传、下载不倒退、不清零、不重复记账，增量与原始计数差完全相等 |
| 账本写入 | `/proc/locks` 中始终只有一个持有原锁文件的写入者 |
| 后台就绪 | 必须具备交接后的新采样及持久化结果 |
| 故障保护 | 原有样本有效时限继续生效，不能延长或伪造心跳；超过 4 秒即关闭成员的网络闸门（只拦公网流量，不停 Core） |
| 用户隔离 | 某位用户的检查失败只影响该用户，不连带其他成员 |
| 失败回退 | 注册尚未开放时可回到固定旧版本后台；不恢复旧数据库 |
| 并发管理 | 交接期间管理入口被实际阻断，revision 与 registry 未变 |

## 已有验证与局限

- 单元测试：39 项协调器测试。模拟主机按真实节奏写入（每 worker 独立相位并有落库延迟），覆盖以下情形：
  - 成功；按最佳相位停止；相位漂移时拒停；
  - standby 失效、管理变更、见证不持久、缺见证或预算不足时中止；管理入口目录他人可写时拒绝预览；在途 RPC；
  - 接棒失败回退；慢回退导致中断；慢退出被强杀；独占的新 writer 不被替换；读取故障；读取器超时后的迟到回复；
  - 切换后的证书同步成功与失败；意外异常的类型记入收据，消息只保留本项目自己的；
  - 近期虚拟机暂停时不可批准；预览后才出现的暂停在任何改动前中止执行；准备期间出现 steal 时不停旧 writer。

  另有 helper 的 v1 证明测试、guard 持久连接测试（旧实现下该测试失败）、guard 的关闸与退出码测试、8 项闸门模块测试，以及 5 项服务器本地证书同步的契约测试。
- 本机真 sing-box 1.14.4（darwin 版）：VLESS/TUIC、双观察者断线重连均通过；订阅后首帧 ≤37 毫秒，之后每秒一帧。
- 一次性容器（Ubuntu 24.04、systemd 255）：真实协调器、真实 unit 模板、真实 root helper，只有 writer/guard/Core 进程是替身。
  - 替身 writer 也按每 worker 独立相位和 0.35 秒落库延迟运行。
  - 成功：在最佳相位停止，成员样本年龄约 0.38 秒；0.10 秒内完成持久化，Core PID 与长 TCP 会话保持。
  - 接棒崩溃：0.08 秒发现，0.17 秒内回到旧 writer，成员保持。
  - 接棒挂起：1.21 秒触发回退，1.33 秒恢复，成员保持。
  - 依赖接管后中断：完整撤回，旧 writer 从未停止。
  - 交接后停止 writer（加入网络闸门之前）：成员约 4.5–5 秒后被 guard 停止，管理员不受影响。
  - 2026-10-26 在新容器中复跑：四个场景全部通过，成功场景在成员样本 0.378 秒时停止旧 writer。
  - 2026-10-26 加入网络闸门后再次复跑：四个场景全部通过。交接后停止 writer，3.5 秒后闸门关闭，经外部地址的流量停止，Core 的 PID、InvocationID 和重启次数不变，管理员不受影响。writer 停止超过 5 秒后再启动，闸门保持关闭，等待对账。回退场景中，成员恢复绑定旧 writer，闸门 drop-in 删除，闸门放行。写入者崩溃后，systemd 3 秒自动重启的 standby 曾在 5 秒内重新接管，这只作为观察记录，不作为依赖。

- GitHub CI：托管 runner 的 `/usr/local/bin` 默认为 0777。首次 CI 演练时，协调器拒绝在这种目录里替换 root 入口，交接中止。这符合设计，但当时收据只写了 Unexpected failure。现在 CI 先把该目录收紧为与目标机一致的 0755，演练也会检查这一前提。
- 局限：替身进程比真实 writer 启动快得多，生产预算必须以预览在目标机上的实测为准；Docker 中需先把根挂载设为 shared，否则 systemd 无法投递 LoadCredential；真实客户端、TUIC 和上线后的现场验收都尚未进行。

## 故障与恢复边界

保留现有连接是正常升级的验收要求，不代表主机故障、网络中断或持续计量故障时还能保证连接。计量故障的保护仍然有效，不能为避免断连而关闭安全检查。

服务器重启后若已没有运行中的普通用户代理，新后台只能进入明确的恢复模式。未知用量保留记录，每位成员分别待对账；恢复一位成员不能解除其他成员的限制。管理员通道独立保留。

注册已开放并分配新用户后，不能再用不认识这些用户的旧后台回退。常规恢复仅关闭注册与个人页面，继续提供已启用用户的订阅、代理和计量。

## 发布边界

独立检查服务、新后台服务、完整实例依赖调整属于阶段 A，需要新的离线包、精确版本与本计划的具体批准。证书来源调整和注册资源属于阶段 B，另行批准；阶段 B 须沿用或明确替换现有的直接 ACME 同步，不能再叠加第二个改写 ExecStart 的 drop-in。现有服务器保持当前版本。

9443 网页服务替换可能短暂影响订阅下载，与已经建立的代理连接分别验收；不能把它们混为同一项结果。
