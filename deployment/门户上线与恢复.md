# 注册门户：保持现有 Core 的交接与恢复

> 2026-10-28 状态更新：服务器已运行 policy v2、公开注册门户及逐用户 guard。本文保留原方案与演练过程；当前部署状态和合并选择以[分支整合与服务器对照](../docs/分支整合与服务器对照-2026-10-28.md)为准。成员继续使用 BindsTo/After 绑定 guard。

**当前仅完成本地开发、单元测试和一次性 systemd 隔离演练，不代表已经上线。** 用户已撤回普通成员维护停用许可：旧的 `portal_upgrade --stage` 配套维护清单不能用于这次切换。不能停止当前名单成员，不能直接重启原 agent，也不能部署之前的 f714 快照。

上线分两个阶段，各自需要新的具体批准（原因见[保持现有代理的升级验收](../docs/保持现有代理的升级验收.md)）：

- **阶段 A：writer 交接**。由 `deployment/coordinator.py` 执行。policy 保持 v1，不新增端口、账号或防火墙规则，也不改 9443 和证书来源。
- **阶段 B：注册资源**。包括 v2 资源池、web 账号、新端口、受管证书和门户；用同样的 standby 机制换到新 release 实例。

## 阶段 A 准备

1. 构建 schema2 离线包。`portal-wheels.lock.json` 中的 9 个 Linux3.12 wheel 已分别与官方 PyPI SHA 核对；除固定版本 protobuf 外均为纯 Python，不在线安装。

   ```sh
   python -m deployment.portal_release --wheelhouse /private/wheels --lock deployment/portal-wheels.lock.json --output /private/new-reviewed-release.tar.gz
   ```

2. 单独批准后离线暂存不可变 release。暂存只新建 `/opt/dazzle-vps/releases/<id>`，不切 `current`，不改策略、unit 或服务，也不打开生产数据库。新 release 尚未安装时，操作者用 root 私有目录中解开的同一个包运行：

   ```sh
   /usr/bin/python3 -I -c "import sys; sys.path.insert(0, '/root/private-extracted-release'); from deployment.coordinator import main; raise SystemExit(main())" --stage --archive /private/new-reviewed-release.tar.gz --approval /private/stage-approval.json
   ```

   暂存批准字段为 `version=1, operation=stage_release, approved=true, approval_id, archive_sha256, release_id`。

3. 只读预览（由已暂存的新 release 运行），输出计划及其 SHA：

   ```sh
   /opt/dazzle-vps/releases/<new>/venv/bin/python -I -m deployment.coordinator --preview --new-release-id <new>
   # 可选：--parameters <JSON>，在允许范围内调整已审参数，并写入计划
   ```

   计划列出每个将写入的文件全文与原 SHA、进程身份、锁 inode、账本 revision、实测的旧 writer 冷启动时间和 helper 延迟，以及据此算出的回退预算。存在任一问题时，`ready_for_approval` 为 false。常见问题包括：缺少 TCP 见证、预算不足、有待执行任务、成员接近额度、周期边界临近、unit 来源或依赖与旧 release 不符、最近 24 小时内核报告过虚拟机暂停（`HOST_STALLS`）。管理入口及其目录必须只有 root 可写，因为交接时要原地替换它，否则预览直接报错。

4. 批准文件只绑定这份计划：

   ```json
   {"version": 1, "operation": "live_writer_handoff", "approved": true, "approval_id": "<uuid>",
    "plan_sha256": "<预览输出>",
    "acknowledgements": {"abort_rather_than_restart_core": true, "fallback_is_best_effort_fail_closed": true,
                         "registration_stays_closed": true}}
   ```

5. 交接时每个现有成员都要保持一条真实 VLESS TCP 连接，用作见证。然后由新 release 一次运行：

   ```sh
   systemd-run --unit=dazzle-vps-handoff --collect --wait --pipe /opt/dazzle-vps/releases/<new>/venv/bin/python -I -m deployment.coordinator --apply --plan /private/plan.json --approval /private/approval.json
   ```

   每一步的执行顺序、闸门与预算规则见验收文档。收据位于 `/etc/dazzle-vps/handoff/<plan_id>/receipt.json`，私密备份 `pre-handoff.sqlite3` 只作证据，不会自动恢复。意外异常的类型和消息记入收据的 `unexpected_error`。

阶段 A 写入或替换的全部内容如下：

- `/etc/dazzle-vps/handoff/previous-policy-v1.json`
- `/etc/dazzle-vps/guard-proofs/`
- `dazzle-vps-meter-guard@.service`（固定新 release）
- `dazzle-vps-writer@.service`（实例名即 release ID）
- `dazzle-vps-agent.service` 的回退定义（固定旧 release 与 v1 快照）
- 每个现有成员的完整 `dazzle-proxy@<id>.service`
- 完成后：`current`；绑定 guard 的 `dazzle-proxy@.service` 模板；旧 writer 取消开机启动、新 writer 启用
- 交接期间临时替换 `/usr/local/bin/dazzle-vps-control`，结束时恢复原字节

完成后运行一次已安装的证书同步，核对它在新 release 下仍然成功；失败不撤回交接，收据单独标记。证书来源不变。

不触碰的内容：SSH、防火墙、9443、证书来源、Core 二进制、账号和数据库内容。

若协调器被强制杀死，管理入口可能仍处于保持状态。保持脚本只输出 `CONTROL_UNAVAILABLE`；按收据核对后，把 launcher 恢复为安装器原内容即可。

## 两种恢复边界

**交接未成功、注册尚未开放且未分配新用户：** 协调器先停止未就绪的新 writer（含 auto-restart 状态），确认它已退出并释放同一把锁。然后用原不可变 release 和 v1 快照启动旧 writer。只有旧 writer 重新获得真实新鲜样本后，才恢复成员对它的完整依赖，再停止 guard。整个过程不恢复 DB、计数、邮箱记录或撤销墓碑。若无法在安全时效内完成，收据如实记录受影响成员，fail-closed 保护不关闭。新 writer 一旦已独占锁就不再回退。

**已经启用新注册或分配新用户（阶段 B 之后）：** 不再回退到旧 v1 程序和策略。常规一键回退只重启 9443 进入 subscription-only，关闭注册、登录和个人页面；新 writer、每成员 guard、已启用代理、订阅、账本、资源池与有效证书都保留。

```sh
python -m deployment.portal_upgrade --rollback
```

该命令先给出回退预览和 SHA，只有绑定该预览的单独 approval 才执行。未知的既有 override 拒绝覆盖；不修改防火墙、SSH 或原账户权限，不重新创建旧 writer alias。

## 阶段 B 的资源与权限范围（另行批准）

保留原有管理员和成员的 worker UUID、Core PID、凭据、配置、端口、计数与账本。新增五个 member 槽：24432–24436 TCP/UDP，统计端口 34432–34436 仅监听回环。未放行的申请不占槽位。网页及日常审核不能扩容 root policy，也不能修改防火墙或 SSH。

独立的 `dazzle-web` 不加入代理组，不读账本或 SMTP；网页只调用按 peer UID 授权的私有 Unix Socket。

- **TLS 映射**：用 `BindReadOnlyPaths=/etc/dazzle-vps/web-tls:/run/dazzle-vps-web-tls` 把证书目录只读映射进服务命名空间，CLI 实际读取 `/run/dazzle-vps-web-tls`。这样不必放宽父目录 ACL，也不能把 web 加入 dazzle-vps 组；目录绑定还能让原子换证即时可见。
- **门户 unit**：不再 `Requires=` 任何 writer，未来的 writer 交接不会连带停止 9443；交接期间门户对账户操作返回 503。

**证书来源已在线上改为直接读取 ACME lineage**（2026-10-25，在发布包之外安装，原文见 [`server/certsync/`](../server/certsync/)）。`20-direct-acme.conf` 让同步服务以 `current` 的解释器运行服务器本地脚本，脚本只接受 `qqg-ip` 同一代的 live/archive 文件对；certbot 部署钩子在续期后触发同步。阶段 B 若改用本仓库的 `managed-certsync.conf`，必须先替换现有 drop-in，不能并存：两个 drop-in 都会清空并改写 ExecStart，最终生效的只取决于文件名排序。证书源始终是实际核对过的 certbot lineage，不重建已删除的 s-box；独立的项目副本继续接受有效的证书轮换，不能被覆盖为旧证书。

旧服务或文件若已由管理员清理，基线如实保存 not-found、inactive 和缺失状态，并要求明确的管理员清理依据。不能伪造 healthy legacy，也不能为通过历史安装器的断言而恢复旧服务。

## 隔离 Linux 验收

两个脚本都只允许在隔离的 GitHub Ubuntu24.04 runner 或带标记的专用容器中，以 root 运行，并要求 PID1 为 systemd：

```sh
sudo --preserve-env=GITHUB_ACTIONS python3 deployment/tests/systemd_handoff/integration.py
sudo --preserve-env=GITHUB_ACTIONS python3 deployment/tests/systemd_handoff/rehearsal.py
```

- `integration.py`：使用随机前缀的 fixture unit 验证底层机制，覆盖依赖迁移不重启 Core、单 TCP 会话、只读 WAL、单 writer 对账、失败回旧、guard 隔离、5 秒过期、API-only 自举，以及 TLS 只读目录绑定与热更新。
- `rehearsal.py`：使用真实协调器、未修改的生产 unit 模板、真实 root helper 和 systemd，只有 writer/guard/Core 进程是替身，演练成功、接棒崩溃、接棒挂起和依赖接管后中断四种情形。若主机上已存在任何生产路径、unit 或账号，脚本会拒绝运行，结束时删除自己创建的全部内容。在 Docker 中须先执行 `mount --make-rshared /`。`/usr/local/bin` 必须为 root 所有且他人不可写；GitHub 托管 runner 默认是 0777，CI 会先收紧为 0755。

2026-10-25 已在一次性容器（systemd 255）中通过两者；2026-10-26 修复上述 CI 问题后，在新容器中复跑演练，四个场景全部通过。结果保存在私密资料中。演练不替代生产的预览实测、现场验收和真实客户端或 TUIC 验收。
