# 公开注册门户：独立审批、资源池与恢复

本轮源码和隔离测试不代表已经上线。原443/8443、SSH、管理员代理、现有账户和统计账本不变。不能将本次扩展交给旧的program-only updater：新增账号、root policy v2、受限Socket、依赖及服务身份都需要单独审批。

## 本次具体变更

- 保留两个原worker的UUID和端口，新增五个明确登记的member槽：24432–24436 TCP/UDP；统计34432–34436仅回环。未审核注册不占用槽位，未启用槽位不运行核心。
- v2 policy仅允许该组端口配对，不允许网页或普通RPC扩大资源池；旧v1仍可加载。五个worker UUID从实例身份和固定端口确定，重复预览不会生成另一批身份。
- 新增无登录权限的dazzle-web账号/组，使用预先核对未占用的明确UID/GID，不加入dazzle-vps、不接触代理配置或账本。它只读取独立web-tls副本，并调用受限portal Unix Socket。
- Agent补充dazzle-web组；/run/dazzle-vps-portal目录为agent拥有、web组、2750，Socket0660并核验peer UID。tmpfiles保证重启后目录恢复，公网进程不能接触原root helper Socket。
- 9443改由单进程ASGI门户承载，保留原订阅路径、TLS验证和热更新；用户网页没有任何管理员接口。原8443和443服务不改。

## 离线发布与预览

使用portal_release模块构建独立schema2发布包。锁文件为JSON数组，每项必须有name、version、filename、sha256；只接受明确白名单、稳定精确版本、经过哈希核对的wheel。除原固定Linux protobuf外均为纯Python，不加入Pillow、uvloop、httptools或运行时在线安装。

```sh
python -m deployment.portal_release --wheelhouse /private/wheels --lock /private/portal-lock.json --output /private/portal-release.tar.gz
```

预览需要现场只读基线、原安装授权、不可变SQLite备份及其SHA、现有policy和明确的候选portal UID。默认预览不会打开生产数据库，检查迁移仅在备份的私有临时副本进行。服务商安全组/网络条件未核对时显示未就绪，不从SSH猜测已放行。

```sh
python -m deployment.portal_upgrade --archive /private/portal-release.tar.gz --database-backup /private/ledger-backup.sqlite3 --backup-sha256 BACKUP_SHA256 --portal-uid REVIEWED_UID --baseline /private/portal-baseline.json
```

预览列出具体五个槽位、十个TCP/UDP授权、账号UID/GID、配置/服务文件、备份摘要、原代理PID及维护影响。它不会修改防火墙、服务商控制台或SSH。明确批准必须绑定这个预览的SHA，不能把本地生成的approved字段当作人类已同意。

## 维护与现场切换

**当前普通用户unit有BindsTo=agent，重启agent会停普通用户。** 升级需要新agent启动受限Socket，因此必须额外明确批准普通用户短暂停用/恢复；不能为了声称零中断而删除fail-closed依赖。旧443/8443及独立管理员unit应保持PID不变。

1. 先核对原代理与管理员健康、文件摘要、现有用户状态/修订号、空闲端口、系统内存及服务商网络条件。记录实际影响并确认具体审批。
2. 暂停App轮询，使用现有RPC停用将维护的普通用户；记录原授权及最新计量，保存一致性SQLite备份和root policy/registry/units/证书摘要到root私有目录。
3. 使用带精确审批文件的--stage准备新不可变release及离线venv，并在备份副本验证增量迁移。此操作仍不切current、不创建账号、不启动服务、不改防火墙。
4. 按审核清单创建dazzle-web及目录，安装四份精确服务/临时目录配置。逐条核对已有规则，只新增已批准且尚不存在的五个端口TCP/UDP授权；不得重写原规则注释，不重置、重载或删除已有规则；统计端口不放公网。若预览发现匹配规则，须先单独审核处理，不能直接把它们标记为本程序新增。
5. 停止新agent/9443及root helper并排空已受理请求，旧代理与管理员worker继续。保留旧release，将新policy v2和current切换到已检查release；registry原记录及墓碑不改。
6. 执行tmpfiles初始化，验证独立TLS副本并运行certsync，启动新helper/agent/9443。确认数据库完整、两个旧worker绑定不变、五个新worker仍未启用、注册默认关闭。
7. 新采集恢复可信后，仅恢复这次维护前已启用且没有随后被停用/撤销的普通用户。核对维护间隙与用量，不恢复旧DB，不把未知缺口当零。
8. 验证所有旧订阅、代理和SSH；再在App明确开启新注册。邀请测试者自己发送验证码，检查绑定确认邮件不含订阅、个人网页预生成链接审核前403；Mac启用并真正运行后同链接200，后台首次开通邮件包含两条链接。普通停用再恢复不重复首次开通邮件，SMTP接受不等于实际收件。

任何步骤出现摘要变化、账号/端口占用、迁移改动旧账本或不明计量缺口，都停在当前阶段保留证据，不自动回灌数据库或重启原代理。实际切换由操作者按清单执行；工具的stage不会代替这些审批和现场动作。

## 一键安全回退

默认回退仅让9443进入subscription-only：关闭注册、验证码登录和个人网页，保留已启用用户的订阅与代理、agent计量、整个资源池和账本。只重启9443，绝不重启agent或proxy worker，不撤防火墙、不切回不支持v2的旧程序，不覆盖证书或恢复旧DB。

```sh
python -m deployment.portal_upgrade --rollback
```

该命令先输出回退预览及SHA。操作者核对后提供绑定该预览的单独approval文件，再加--approval执行。删除/撤销墓碑保持有效。若需重新开放门户，应单独审核移除subscription-only覆盖文件及注册开关；回退本身不会悄悄重新开放注册。
